# 37. Scope routine verification and gate releases

- Status: Accepted
- Date: 2026-10-30, revised 2026-11-02

Routine changes run verification selected from their dependency evidence instead of every test. Selection is best effort: incomplete evidence widens it to a bounded layer, and only a short list of repository-wide inputs selects full verification. Full release-candidate verification is the only completeness guarantee. Each pull request exposes the selected tests and the reasons for that selection.

Full verification is required for a release candidate. The standard release and frontend and backend deployment entry points must check successful full-verification evidence for the exact candidate commit before publication or deployment. Establish this machine gate before reducing the current routine checks.

The implementation adds a formal-candidate eligibility policy on 2026-10-31. The candidate must equal a freshly confirmed merged PR's final integration SHA on the requested repository's protected `main`, and be reachable from its explicitly resolved `refs/heads/main` commit. An associated intermediate ancestor, an open test merge, or an unmerged producer is ineligible. The initial policy used the complete admitted tree as its verification producer; the trusted-main extension below separates those roles. Configuration hashes are compatibility keys, never authority. An eligible older final snapshot remains usable after main or its producer implementation advances. The existing owner-selected repository option also applies this policy to forks.

Admission checks native repository/base/run/head repository IDs and active PR, linear-history, force-update, and deletion protections before dispatch or protected publication/deployment work. This boundary trusts current native integration governance, including authorized owner, administrator, and configured override authority. It does not prove historical protections or review diligence, and does not require privileged bypass metadata. Ordinary reusable PR verification remains available before formal eligibility.

The standard release command runs on an owner-controlled machine. It fixes the candidate commit, requests or reuses full GitHub Actions verification, and checks the results before creating the Release for that commit. The Pages workflow and backend deployment script each check the candidate's evidence independently before deployment. These checks also cover manual Pages workflow runs and direct use of the backend script. Backend deployment still runs from the owner's machine.

A Release created directly through GitHub's website or a bare CLI command can exist before verification. The deployment gates prevent that Release from deploying an unverified candidate through repository-supported entry points. The pre-publication guarantee applies to the standard release command.

GitHub Actions results are the authoritative evidence for integration and release. Local runs provide focused development feedback and browser reproduction. Running the same verification locally is not a prerequisite for its CI execution.

Full verification covers the union of the former CI, CI Full, and E2E checks: fast and slow tests, Workshop behavior regressions, architecture checks, lint, i18n, type checks, application and Replay Viewer builds, bundle budgets, community-deck checks, the Chromium suite, the browser-local sandbox, and the WebKit smoke tests. The legacy fixed LLM harness was retired on main before implementation of this policy. Its replacement Workshop behavior tests remain part of the current test projects. Paid model acceptance and performance benchmarks remain separate checks selected for the change.

Successful results may be combined across compatible runs for the same candidate commit and verification configuration. Retry failed tasks without repeating other successful tasks. Every required task must actually succeed. Missing, failed, cancelled, or skipped required tasks do not establish a successful release result.

Do not add scheduled full-verification runs. This saves routine execution at the cost of later discovery: a regression outside the selected tests may remain undetected until release-candidate verification.

The scope planner, always-running `verify` gate, canonical candidate catalog, and release/deployment gates implement this policy. The former automatic CI Full, E2E, and duplicate scope-preview workflows are retired. Commands and evidence requirements are in [CI checks operations](../operations/ci-checks.md).

## Routine selection

Path-ownership rules left most changes without narrow evidence. After the 2026-10-31 rules, five of the next six merged PRs still ran the complete catalog because a single new, unlisted or global path fell back to full verification. Development latency outweighs routine completeness, because release-candidate verification already catches what routine selection misses.

- **Unit of selection.** Select complete Vitest files and Playwright spec files, optionally with an existing tag filter, and keep both runners. Individual test cases, coverage instrumentation, and historical coverage maps are not used.
- **Dependency evidence.** Each plan computes a repository-wide static import graph from the head tree, including CSS imports, literal dynamic imports, and a literal `new URL(..., import.meta.url)` that resolves to a source module. A changed file selects every test that depends on it transitively, so new modules, tests, and specs take part without registration. A type-only edge selects no test. Configured Vitest setup files add runtime consumers for their own projects. These implicit setup edges do not propagate generated-artifact reads. Unresolved relative imports retain candidate paths for deleted or renamed modules and also remain incomplete evidence. Traversal stops at the four generated card registries and does not continue into their importers: `shared/cards/register-all.ts`, `shared/cards/catalog.generated.ts`, `shared/cards/major/generated.ts`, and `shared/cards/major/runtime.generated.ts`. A change on that side of the cut selects the tests that reach the changed module without crossing a registry, the tests that literally name its registry key, and the tests that import one of the four registries directly. Mechanism aggregators, including `shared/actions/internal-actions.ts` and `shared/actions/index.ts`, are ordinary graph nodes. The former card-safety set, rule-safety set, and rule browser set are not added.
- **Reads and generated files.** A non-code file or generated artifact selects only the tests that read it directly and the direct tests of a production module that reads it, not that module's transitive dependents. One short list ties generated outputs to their inputs: language packs from `i18n.ref`, and the cards manifest, encyclopedia, and action references from the card sources. A filesystem read matches when the source contains the changed path, a directory prefix, or a glob literal, including a literal `new URL(..., import.meta.url)` that resolves to some other repository path. Local const aliases and path-building initializers are followed with lexical shadowing; runtime parameters remain incomplete evidence. A read with no such literal is incomplete evidence.
- **Browser evidence.** An import from a spec to source counts only when it is direct, not when it passes through a shared test helper, even if the consuming spec has a coverage declaration. A spec declares the path prefixes it covers with a leading `// @covers` comment. A declaration names directories that spec exercises and does not name a whole layer such as `shared/`. A prefix that matches nothing warns and is ignored. A changed file selects specs whose declaration matches. Otherwise the plan walks importers and stops at the first file with a declaration. The walk uses the routine browser smoke set when it reaches `client/main.tsx`, or the matched specs exceed one third of all specs. Reaching `replay-viewer/src/main.tsx` selects `e2e-tests/replay-viewer.spec.ts` and `e2e-tests/replay-viewer-csp.spec.ts` instead of that smoke set. `client/sandbox/SandboxApp.tsx` is not an entry, so the walk continues. A file that reaches both entries selects both results. A file imported by nothing selects no spec. A spec that declares nothing is not incomplete evidence. The smoke-set list lives with the planner, so changing it is a full trigger.
- **Bounded widening.** An unresolved import, a source file that cannot be parsed, or a filesystem read with no matchable literal adds a warning and widens the affected selection to its Vitest project or the routine browser smoke set. Widening never fails planning and never selects the complete catalog.
- **Full triggers.** Only dependency and workspace manifests, root test and build configuration, CI workflows, and the verification planner and gate select the complete catalog. Every other file selects through the rules above.
- **Always-on tasks.** A change that is not documentation-only also selects the quality and build catalog tasks. A documentation-only change selects only the tests that read those documents; a valid empty documentation plan passes with every execution slot skipped.
- **Failures.** A planner exception selects the complete catalog and reports the error. `verify` fails only for a failing selected test, a missing or skipped selected task, or execution evidence that differs from the plan.
- **Execution.** Selected Vitest files are sorted by path and project, then distributed round-robin into at most three jobs, `units-1`, `units-2`, and `units-3`. Unused slots are skipped. Browser tuples are sorted by file, engine and grep, then distributed across `browser-1` through `browser-4`. Each tuple remains intact and executes once. `verify` stays the only required check and still checks partition identity and execution evidence. Each browser partition prepares services once, creates its private environment through tsx, and starts the app once through restart-local.sh. The launcher builds the Replay Viewer and its required language packs, cards manifest, encyclopedia, and action references together, without a second standalone manifest build. Environment credentials are removed on stop or failed startup. Browser reports must contain completed results for the selected spec files; intentionally skipped cases remain visible, while empty, missing, extra, and failed results block completion. It builds the hosted frontend, without a separate typecheck, only when a selected spec depends on that build. Routine browser runs retry once; a test that passes only on retry is named in that partition's job summary, counts as flaky, and still passes. Release-candidate browser runs do not retry.
- **Routine browser smoke set.** At most five file-and-grep entries cover login, a two-player WebSocket game that builds a room, one game screen, and the WebKit scenario matrix. Coverage determines the entries, and selectors restrict the cases within each spec. The runtime target is about two minutes, measured in hosted CI.
- **Latency targets.** Measured from a push to the `verify` conclusion, excluding GitHub queueing and manual retries: 8 minutes for a single-area change and 12 minutes for a cross-module change. These targets require hosted measurement. A full trigger takes the complete catalog's duration.
- **Catalog balance.** The complete catalog keeps its task IDs and coverage. Its Chromium shards, the routine Vitest jobs, and the four routine browser partitions use sorted file-count assignment. Lane counts differ by at most one. A candidate SHA and its Git-derived verification configuration determine fixed task membership across compatible retries. Actual timings remain generated observations rather than scheduling inputs. No timing-data file requires Git maintenance, and adding a test does not require updating estimates. Changes to the partition algorithm remain full triggers.
- **Local reuse.** `pnpm verify affected` compares `HEAD` with its merge-base against `origin/main`, plus staged, unstaged, and untracked files that are not gitignored. It prepares the manifest and any required services, runs the plan's Vitest selection locally, prints selection reasons and warnings, and prints the browser selection unless asked to run it. A full trigger prints the reason and does not launch the complete catalog locally.

Prepared dependency graphs are cached only for a matching source fingerprint. Each plan summary explains selection by changed path, runtime imports, registry evidence, direct reads, and browser evidence.

The routine planner, partitioning, and execution may be restructured. `verify` remains the only required check. The complete catalog's task IDs and coverage, and the release and deployment gates, stay unchanged. Cross-commit result reuse is out of scope.

## Independent prerelease channel

The decisions in issues #1645 and #1655 extend this policy with a separate prerelease candidate type. Stable admission still requires a final merged-PR snapshot reachable from protected main. Prerelease admission uses an immutable integration snapshot and explicit feature/dependency provenance; it can precede main integration.

Routine main and prerelease events share the canonical scope plan. Manual prerelease publication still requires every complete catalog task. Trusted main controls orchestration and receipt acceptance; candidate execution receives no formal write or deployment credentials. Receipts bind native repository identity, channel, SHA, candidate and producer configuration, and a compatible producer reachable from protected main. Configuration equality never grants trust by itself. Missing, failed, cancelled, skipped, or incompatible required work blocks publication.

Only the owner main-synchronization command may rewrite prerelease, with the explicit old SHA lease and unchanged feature sources. Reviewed PRs add or remove features. Main, immutable candidates, and release tags never move through this exception. Selected features or dependency groups enter main through their own reviewed PRs and obtain evidence for the actual new main SHA.

Prerelease versions use vX.Y.Z-beta.N and the native prerelease flag. Channel and target metadata bind artifacts; a suffix is not authorization. Formal Pages independently rejects native prerelease requests. Publication, installation, and live acceptance remain separate stages. Effective native protections and real target isolation must be configured and read back in the owner tickets; source changes alone do not prove those settings.

## Trusted stable main producer

Formal stable verification now separates fixed protected-main producer P from candidate payload C. C still requires the final merged/main-reachable snapshot admission before privileged setup. All controller, setup, source checking and finalization come from P. Native main-only dispatch binds repository/channel/C/P and both configuration trees. Ordinary CI uses candidate-rehearsal.yml to exercise the current implementation's complete isolation catalog before merge; that workflow purpose/path cannot authorize deployment.

Legacy stable receipts are limited to admitted ancestors of the trusted fixed 53b8a0ccf5649ce3bb7084303f0677e46c1d20e7 cutoff and their original native producer/configuration. A candidate marker cannot select policy. All new P runs isolate every C. A new native P/C attempt, even incomplete or configuration-incompatible, blocks fallback to old green. This retains bounded historical recovery without letting future source downgrade the gate. Policy P itself remains under protected-main governance and owner/admin trust.

## Explicit owner-local stable verification

The native repository User owner may explicitly authorize complete local candidate verification through `pnpm release --local-verification`. This is a separate proof type. It does not create or imitate GitHub workflow/job evidence, and it does not change prerelease admission or routine required checks.

The owner receipt binds repository identity, the actual tested commit, raw source tree, candidate and producer verification configurations, all ten canonical tasks and actual commands, successful exits, log hashes, timestamps and a supported Node environment. After a same-tree rebase, the publisher may rebind the final merged-main candidate while retaining the tested SHA. A different source tree or configuration requires new verification.

Authority comes from the native owner's independent `owner-local-verification` commit status and a digest-bound JSON asset in the exact-candidate formal Release. Status creator, Release author and asset uploader must all match the native User owner ID. The same gate revalidates this proof for publication, Pages, backend delivery and private image production. Only this explicit mode resumes its own matching draft. Real GitHub image builds, immutable provenance, private registry checks and runtime delivery guards remain required. The separate Bug Report deployment-feedback proof still requires native GitHub job evidence.

Status selection considers only the native owner's matching context. The owner's latest non-success withdraws local authorization and returns to native GitHub candidate evidence; it never restores an older local success. Foreign statuses cannot override that choice. Malformed latest owner-success evidence remains a blocking error.
