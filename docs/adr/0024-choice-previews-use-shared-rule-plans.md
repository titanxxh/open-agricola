# Choice previews use shared rule plans and authoritative spatial targets

- Status: Accepted
- Date: 2026-10-09

Choice Preview derives from the executable semantics of shared rule primitives. Cards can migrate opaque purchase-path or scheduled-offer rules into those primitives, but must not maintain a separate presentation implementation of the same effects. Original Payment Path identity binds a purchase outcome even when discounts change the resources actually paid. Shared plan composition preserves effect order and optionality rather than guessing consequences from text, card IDs, or opaque choice values.

The generic preview layer may project declared deterministic storage operations onto a detached copy and read existing source-card scoring queries. It reports the current source-card scoring contribution change, not a prediction of the entire branch's final score. It does not run arbitrary card callbacks, advance a cloned Engine through later choices, or change admission decisions. Future schedules use the same target filtering as execution and distinguish received resources, optional actions, conditional rewards, and purchase offers. Shared scheduling primitives own preview attribution while existing queue execution semantics remain intact.

Farm target choices carry backend-declared legal targets and opaque selection bindings. Players select ordinary targets directly on their farm, and Card Field targets on their displayed crop slots. Multiple slots belonging to one Logical Field retain one field identity. A target with more than one legal alternative requires an explicit alternative selection; the client never picks the first binding or derives legality from card-specific strings.

The rejected alternatives were card-owned preview callbacks, a second card-specific presentation registry, and general speculative execution of existing callbacks. The first two duplicate rule knowledge; the third adds isolation, hidden-information, and execution-budget concerns without providing an inspectable shared rule contract. See ADR-0015 for current-step admission, ADR-0018 for Future Schedule target identity, ADR-0020 for hidden round information, and ADR-0023 for explicit state visibility.

## Validation

Payment, pending choices, deferred effects, and multistep flows require Session tests under `docs/CARD_TEST_TEMPLATE.md`; direct algorithm tests supplement rather than replace them. Each scenario starts from a fresh seeded two-player GameSession. Use three players for E139, C132, and B146, four for B152, and five for D180 to respect printed player counts and available target spaces. Explicitly set every player's two hands to `['__test_placeholder__']`, adding the target card for purchase scenarios and explicitly setting played cards for reaction scenarios. Start with two workers at home, empty occupation/minor played zones, a wooden two-room house, unoccupied action spaces, no fields, terrain, stables or future entries, and empty cardStates. Baseline inventory is 20 each of food, wood, clay, reed and stone, with zero crops and animals; Farmers of the Moor scenarios enable the variant and set fuel to 20. Every exception below is an explicit fixture override.

After every public command assert `ok`, authoritative state/resource/cardStates or field changes, interaction ownership and candidates, actual action/resource logs, and relevant score contributions. Repeated preview reads must not spend resources, queue offers, change farm/card state, advance RNG or history, emit logs, or progress the interaction. Also cover skip/cancel, unaffordable candidates, unavailable targets, exhausted supplies, round-14 filtering, nested anytime refresh, undo, and current snapshot restoration. Preserve public/private projection and unrevealed round identity masking.

Shared algorithm tests cover exact targets and prefixes using execution's normalizer, preview composition without repeated gains, deterministic storage/scoring projection without live mutation, semantic labels and source identity, mixed-crop field contents, and multiple bindings for one spatial target. UI tests use real Session responses in both locales. E2E covers ordinary farm and Card Field direct clicks, rejection of noncandidates, explicit alternatives when a target has several bindings, optional skip, and representative nonspatial choices at desktop and mobile widths. Check existing Moor special-action and farm-selection surfaces for regressions. Restart with `./restart-local.sh`, verify real browser/API behavior, then run relevant Session tests, fast tests, lint, build, and applicable architecture/prompt guards. Record preview timing on the largest fixed choice fixture without introducing whole-Engine speculative execution.

The fixed M131 fixture has 24 choices with four offers each. On the local ARM64 host, 30 seeded purchase commands (including preview generation, scoring and response assembly) measured a median of 4.46 ms and p95 of 13.75 ms. This is a local command measurement, not a production transport or browser latency claim. Browser coverage uses a one-player Moor fixture only for the multiple-physical-card binding case; ordinary fixtures remain two-player.
