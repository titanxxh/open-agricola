# Card-owned state has explicit contributions, visibility, and presentation

- Status: Accepted
- Date: 2026-10-06

Card-local state remains owned by its Card Source. Shared rule paths consume deterministic read-only Card Rule Contributions instead of recognizing individual cards or interpreting their private storage. Supply usage, standing special stables, and scoring quantity adjustments use generic aggregation; existing animal-zone contributions are reused where they already describe the required facts. Pure farmyard geometry consumes computed generic inputs without loading card implementations. This rejects replacing the current card-local state with another writable supply, stable, or scoring summary.

Card-local internal state is not sent to ordinary viewers by default, including the player who owns that state. Card State must distinguish internal rule storage, explicitly public facts, and explicitly player-private information. Normal synchronization and seat perspectives expose only the declared public and player-private information for their audience. Every viewer projection must preserve that distinction across snapshots, events, history, and Bug Report evidence. An internal or private write must not expose its value through a public event or historical presentation. This replaces both default-public internal fields with per-card removal exceptions and independent redaction patches in product routes. Player-private information belongs to the player storing it rather than the current holder of a passing card.

The complete authoritative state remains available for rule execution, active recovery, undo, and Replay recording. As required by ADR-0010 and ADR-0011, a completed Replay seat perspective shows the information visible to that player, while the all-open perspective may show the complete recorded rule state. This decision does not authorize deleting private values from recovery or Replay storage.

Dynamic Card State Presentation uses structured generic data contributed by the owning card. Frontend renderers consume counts, resource groups, animal markers, and source identity without recognizing card IDs to interpret private storage. Static card names, artwork, and translations remain ordinary Card Display metadata. Presentation is derived from the authoritative Card State rather than maintained as another writable rule truth.

Anytime Window permissions are explicit properties of the current waiting interaction rather than meanings inferred from prompt keys. Existing Hide Farmer, exchange, and bake-bread windows retain their current allowed and blocked actions. A window declaration applies only to the waiting step that declares it and is not inherited automatically by a nested choice. Hide Farmer therefore allows exchange before accepting its optional effect, while its subsequent resource-quantity selection remains closed to anytime actions. Shared Session policy consumes generic window data without knowing which card supplied it.

Architecture checks must cover common single-card state dependencies and card-prompt policy branches in shared rules, sessions, projections, server code, and frontend code. Other dependencies of the same kind found during this repair are included in the cleanup rather than retained through a migration allowlist. Legitimate metadata and declarative printed targets may have narrow, reasoned exceptions. The checks use ordinary repository syntax and source discovery, not whole-program dataflow analysis.

The rejected alternatives were moving existing card-local facts into shared writable summaries, leaving internal fields public unless a card author remembers to hide each key, retaining frontend branches that interpret individual cards' internal fields, preserving prompt-key authorization outside the Hide Farmer special case, and grandfathering equivalent shared-path dependencies through a migration baseline. They would spread state ownership, preserve the hidden-cache omission risk, or leave rule decisions coupled to card identity and presentation text. The concrete state containers, contribution interfaces, and migration tests remain implementation design work; this ADR records the confirmed ownership, visibility, presentation, window-policy, and checking boundaries.
